# 独立桌面软件、统一 MCP 与 Docker 成品验收

## 背景和实际变化

用户明确本机应是独立软件、界面内容尽量可点且有合理反馈、文案面向使用者、后续每个工具都能被 AI 调用，并已启动 Docker 服务。保留共享前后端，新增桌面与 stdio 适配，未更换业务技术或引入微服务。

- CLI 默认 desktop，显式 serve 保留浏览器开发/Docker；Windows pywebview/WebView2 使用随机回环端口、原生请求凭据、受限导航，无通用 JS/Python 桥。窗口退出结束本实例服务，不误杀其他进程。
- PyInstaller onedir 同包生成 GUI MTools.exe 与控制台 MToolsAI.exe，前端和清单随包；补源码启动、桌面构建和实际窗口验收脚本。成品由当前 Windows x64 构建，未发布/签名。
- 可信装配集中在 bootstrap/tools.py；OperationHandler 绑定模型与业务函数，ToolRuntime 共用参数/结果验证、4 并发、操作超时与安全日志。清单 schema 名必须匹配正式模型。
- 官方 MCP 1.x stdio 自动发现可用操作，稳定版本名称、输入/输出 schema、annotations、structuredContent/JSON 文本及统一安全错误。当前只放行 read-only，其他副作用拒绝执行，模型传入 confirmed 不能授权。
- AI 助手页生成源码、桌面或同 Docker 宿主的真实连接配置；配置获取不表示已连接任何第三方客户端。
- 整卡进入工具，标签筛选，状态、隐私、版本和提示可点击解释；帮助卡导航、折叠说明、弹窗 Escape/焦点恢复。普通操作文案移除服务端/源码细节。
- 主题从 localStorage 迁为 preferences.json 原子保存，跨随机端口和重启；保存失败向用户反馈。无输入历史、数据库或持久任务。

## 实现过程中的问题与修复证据

真实窗口发现 WebView2 导航事件需要在 UI 线程装配；改为 native.Invoke 后重新执行实际操作及外部导航阻断，未再出现线程异常。严格 CSP 保留，无 unsafe-eval；窗口验证使用 run_js，成品验收仅为测试进程开启本机调试端口。

Windows stdio 不能直接复用控制台文本输入包装；实际 SDK 握手出现等待。改为明确 UTF-8 包装底层缓冲，在退出时 detach，避免 SDK 包装回收关闭共享 stdout。源码和重新打包成品均以真实客户端重新验证；协议 stdout 不混入日志。

打包时不收集不需要的 MCP CLI，避免其可选依赖导入终止；使用双入口共享依赖目录。只修改与新需求相关的代码，未升级既有前端依赖。
