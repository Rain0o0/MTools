# ADR-0001：模块化本地网页工具箱与默认技术路线

## 背景

用户需要持续添加不同类型的工具，允许功能间存在联系和模块复用，倾向软件内嵌本地网页与 Python 后端。最终需要源码和 Docker 交付，以及便于后续 AI 按类型/功能/时间读取并维护的详细文档。本轮只交付规范。

## 决定

采用模块化单体，默认 Python/FastAPI、React/TypeScript/Vite，桌面壳优先考虑 pywebview 加载本机服务。Docker 提供同一业务核心和网页，通过浏览器使用。版本及依赖在首次实现时核验、锁定，不在本轮安装。

按平台、契约、工具、共享能力、环境适配和装配边界组织。工具清单、操作契约与公开能力调用承担扩展边界；首期工具受信任并随应用构建。共享层不反向依赖工具，工具间不导入内部实现。

允许纯前端、外部 CLI 和其他语言模块，统一接入契约与权限。桌面原生能力通过适配器提供，清单说明各运行形态的支持范围。

根 AGENTS.md 作为 AI 入口，专项规范按任务读取；当前功能文档与历史工作记录分开，问题修复验证后从当前清单删除。

## 候选方案与取舍

| 方案 | 评估 |
| --- | --- |
| Python 本地服务 + pywebview | 顺应用户倾向，源码与桌面可共享服务；需验证 WebView、会话安全与打包 |
| Tauri 等其他桌面壳 | 如分发体积、系统集成或安全能力实测更符合目标，可替换壳；不据此迁移业务逻辑 |
| Electron | 可选，但引入额外运行时与打包成本需有实际收益 |
| 全原生界面 | 当前会削弱网页与 Docker 界面的共享收益，暂不作为默认路线 |
| 微服务/任意第三方插件 | 当前规模无明确收益，增加运维、隔离与协议成本，按需求再评估 |

这是当前项目设计选择，不是已完成的性能或兼容性比较；后续技术替换需基于真实需求和验证。

## 收益与代价

可先完成一个工具再扩展，统一文档与协议，避免多套业务实现。代价是需要管理本机服务生命周期、环境能力差异、依赖可用性、契约版本和任务副作用。

本方案不自动提供沙箱、热安装、远程多用户或多实例任务一致性；这些能力需要独立设计和验收。SQLite 与单实例是早期默认，存储或并发规模变化时重新评估。

## 验证与重新评估条件

首个工具验证源码和 Docker，共享前端与 API；桌面阶段验证 Windows 启动/退出与 WebView。第二个工具证明共享模块或公开能力组合的实际可用性。

若桌面分发要求、跨平台兼容、核心性能、远程多用户、插件信任或任务并发条件发生显著变化，新增 ADR 替代相关决定。相关约束见 [架构规范](../standards/architecture.md)，阶段验收见 [路线图](../project/roadmap.md)。
