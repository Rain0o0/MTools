# 文档分类、检索与维护规范

文档是可持续维护的项目事实库。按功能组织当前信息，按时间记录变化；不通过复制所有旧内容来体现“详细”。每个有意义的开发步骤必须记录结果与验证，同一批微小操作合并为一份工作记录。

## 1. 分类与唯一事实来源

| 类别 | 路径 | 内容与更新方式 |
| --- | --- | --- |
| AI 总入口 | AGENTS.md | 底线、阅读路由；保持简短稳定 |
| 专项规范 | docs/standards/ | 长期规则，按领域维护当前有效版本 |
| 项目状态 | docs/project/status.md | 实际实现、验证与当前边界 |
| 待办路线 | docs/project/roadmap.md | 仅未完成工作，完成后从清单移除 |
| 功能当前说明 | docs/features/{feature_id}/ | 当前行为、设计、接口、使用和限制 |
| 环境/跨功能手册 | docs/guides/ | 安装、运行、升级、备份、整体使用 |
| 当前缺陷 | docs/issues/open.md | 仅已确认且仍未解决的问题 |
| 设计决定 | docs/adr/ | 重大决定、背景与替代关系 |
| 时间事实 | docs/worklog/YYYY/MM/ | 每批变更、验证、文档维护、未完成项 |
| 用户更新 | CHANGELOG.md | 面向使用者的变化和兼容性 |
| 附件 | docs/assets/{feature_id}/ | 有价值截图/小型示例，有来源链接 |
| 历史文档 | docs/archive/ | 确需保留的旧手册，标为 archived 并指向替代 |

一个事实只维护一个权威位置，其他文档链接过去。例如当前问题正文只在 open.md，功能文档只链接其稳定锚点；某次修复摘要只记日期日志，不复制完整旧问题。

按功能维护 overview.md（用途、状态、结构、契约、限制）和 usage.md（面向用户的当前操作）。内容足够复杂时拆 interfaces.md、design.md 等，拆分后更新索引，禁止空文档凑齐目录。

## 2. 元数据与命名

docs/ 下的正式 Markdown 使用 YAML front matter，至少包含 doc_id、title、kind、status、updated、tags；功能文档追加 feature_id，工具文档追加 tool_id；日期记录使用 date，可追加 related 与 supersedes。

- doc_id 全仓唯一且长期稳定，如 STD-UI、FEAT-text-normalizer、GUIDE-text-normalizer、ADR-0002、LOG-20261015-01。
- kind 使用 standard、index、feature、guide、status、plan、issues、decision、worklog、template。
- status 只表示文档是否有效：active、draft、superseded、archived、template。实现状态另用 implementation，取 planned、in_progress、implemented、deprecated，避免把有效规范误认为已实现软件。
- updated 只在内容实质改变时更新，使用 YYYY-MM-DD；日期/日志统一 Asia/Shanghai。机器时间戳保留时区，历史日志日期不随以后引用而变化。
- tags 使用稳定英文关键词；正文保留准确的中文功能名称、公开接口、模块和错误码，帮助关键词检索。
- 路径用小写英文、kebab-case；代码中的 Python 包使用 snake_case，并记录与 tool_id 的映射。
- 工作记录命名 YYYY-MM-DD-NN-topic.md，同日全项目 NN 顺序递增；多功能变更列 related，不把同一记录复制到多个功能目录。
- 模板 doc_id 用 TPL-*，复制时换成新 ID，并移除模板提示和不适用空节。

AGENTS.md、根 README.md、CHANGELOG.md 不强制 front matter，保持入口易读。

## 3. 功能记录的详细程度

功能当前文档说明：用户目标、支持形态、输入输出、操作规则、模块/复用边界、参数默认值、依赖、权限、限制、失败恢复、验证案例及相关链接。

设计中内容与已验证行为分节标注。已实现后删除过时设想，把适用说明改成当前事实；不能一边保留旧操作步骤，一边用顶部一句“已更新”掩盖矛盾。

使用指南提供前提、可照做步骤、示例输入/输出、结果位置和排查路径。命令附工作目录、适用系统和真实观察；对尚不存在的入口，只写待实现要求，禁止虚构启动命令。

每批工作记录说明触发背景、涉及 ID/模块、实际变更、为什么这样改、检查结果、文档同步、遗留与下一步。记录每个有意义步骤的产出；不要抄录整个终端会话或逐行编辑过程。

## 4. 问题生命周期与删除规则

当前问题条目包含稳定 issue_id、严重性、关联 ID、受影响版本/模式、复现步骤、预期与实际、影响、证据、临时绕过、下一项验证与阻碍。猜测先标“待调查”；路线图中的未做功能不是缺陷。

~~~text
确认问题 → 写入 open.md → 修复 → 原条件复现验证/必要回归
         → 验证不足：保留并注明待验证项
         → 验证完成：删除当前条目、修正当前说明、写简短修复摘要
~~~

- 删除发生在修复完成且验证足够之后，不能仅凭改了代码、异常暂未出现或测试被跳过关闭。
- 验证完成后从 open.md 删除整个条目，更新数量、索引与相关锚点；其他当前文档中的“已知问题”和临时绕过也需删除或修正。
- 不建立长期堆积的 closed.md，不把已关闭问题全文迁移到归档；CHANGELOG/工作记录保留 issue_id、修复结论与验证摘要即可。历史日志中的当时观察是时间事实，不是当前问题清单。
- 清单为空时明确写“当前无已确认未解决问题”，不要保留“已修复”“已关闭”行。
- 通用排错步骤如果仍适用可以保留；与已修复缺陷绑定的过时限制/绕过必须移除。
- 因证据不足、需求变化而撤销问题时同样写明理由后删除，不能伪称修复。

删除当前问题是内容维护，不删除相关源码提交和有效验证历史。

## 5. 决策、历史与归档

ADR 用于主技术路线、公共契约破坏性变更、存储/隔离策略等影响后续实现的决定；普通变量命名和局部样式不写 ADR。

ADR 已采纳后保留历史背景。新方案增加新 ADR，旧 ADR 标 superseded 并链接替代；当前规范同时更新，不能只添加新决定却留下旧规则。历史日志允许修正错字、脱敏和补充验证，但不改写已经发生的事实。

旧手册优先删除可再生成和无历史价值的内容；确需归档才移到 archive，标明失效日期和替代路径，并从当前导航移除。Git 历史承担一般旧版本追溯，不为每次更新复制整份规范。

## 6. 索引与 AI 阅读

docs/README.md 维护分类入口，features/README.md 按功能 ID 维护当前状态与链接，worklog/README.md 按月链接；月份记录多时增加月索引，不把全部日期正文塞入总入口。

AI 先按路由读取规则，再按 feature_id/tool_id/issue_id 精确检索当前事实；需要背景再查 ADR，需要特定日期才查日志。模板、规划和历史内容不能当作当前实现。

链接使用相对路径和稳定标题/显式锚点，不写个人电脑绝对路径作为项目内导航。面向用户交付时可使用绝对文件链接，文档内部保持仓库可移植。

## 7. 每次维护的检查

检查中文编码、LF、元数据 ID 唯一性、状态语义、日期、相对链接、索引、问题数量、示例事实、生成产物来源与敏感信息。删除/移动文件时同时修复所有引用；修改公共规则时检查根阅读路由。

首期可使用一次性检查；骨架阶段按需要建立脚本化文档检查入口，纳入真实开发命令。自动化只能辅助检查，不能证明文档描述与实际行为完全一致。
