# 源码、桌面与 Docker 交付规范

本规范定义交付行为。当前源码、Windows 桌面目录包和 Docker 已完成本机运行验收；桌面为本机默认入口，浏览器服务需显式 serve。事实以 [项目现状](../project/status.md) 为准，构建定义不能代替成品运行验收。

## 1. 三种形态的共同要求

| 形态 | 必须提供 | 特定限制 |
| --- | --- | --- |
| 源码 | 完整业务与前端源码、锁文件、配置样例、真实运行/检查命令 | 开发环境依赖与工具外部依赖需说明 |
| 桌面 | 加载同一前端与服务核心的启动/打包入口、运行时与卸载说明 | 原生系统能力按实际平台声明 |
| Docker | 可重建镜像、Compose、健康检查、持久卷与浏览器使用指南 | 不包含默认桌面 GUI，不自动获得宿主能力 |

源码与 Docker 是必备交付路径，桌面壳是产品目标的运行入口；三者由同一版本的核心实现构建，不维护独立业务副本。

## 2. 源码运行与依赖

首次实现建立并实际验证统一的开发命令入口，再写入 docs/guides/source.md。Windows 可用 PowerShell 脚本，跨平台采用对应命令或统一任务工具，不能只依赖 Bash/Make。

指南应覆盖克隆/解压、支持版本、环境创建、锁定安装、配置、数据路径、前端构建、开发与普通运行、健康检查、停止、排错、测试与清理。明确前端开发代理与生产静态资源模式的区别。

Python 使用 pyproject.toml 与 uv.lock，前端使用 package.json 与 pnpm-lock.yaml；指定受支持运行时和包管理器版本。安装默认尊重锁文件，不在每次运行解析“最新依赖”。外部工具可按功能做可选依赖，缺失时只使相关工具不可用。

业务运行不依赖 Git 存在；源码路径含空格或中文时仍可使用。运行数据默认放应用数据目录，不把程序安装目录当可写数据库目录。源码模式允许显式开发数据目录，但必须忽略生成数据。

## 3. 桌面启动与打包

- 桌面壳负责窗口、可信页面导航、后端进程、原生适配与关闭流程。后端就绪后再显示工作界面，超时/失败有可理解的诊断入口。
- GUI 主循环与后端执行分离，启动与关闭不阻塞 UI；关闭应用按策略取消/结束任务、回收本实例进程，避免孤儿服务。
- 首先验证 Windows WebView 运行时、系统架构与所选 Python/pywebview 组合；具体前置组件写入桌面指南。
- PyInstaller 等打包技术在实际验证后确定；打包包括前端资源、清单、必要数据和依赖授权信息。不能仅以源码启动成功证明打包成功。
- 应用升级不覆盖用户数据；卸载明确默认保留或删除数据的行为。多实例策略、端口冲突和单实例提示由平台统一处理。
- 打包在对应目标环境完成与验收。只有测试后才增加新平台支持；签名、自动更新等按实际分发需要另立设计。

## 4. Docker 基线

默认 Linux 单服务镜像，构建阶段安装前端与后端构建依赖，最终镜像包含已构建静态资源和必要运行依赖。外部工具确需隔离时再增加可选 sidecar/Compose profile。

- Dockerfile 使用多阶段构建、固定基础镜像版本或 digest、锁定依赖；.dockerignore 排除私密数据、缓存和无关文件。
- 默认非 root，限制权限；服务容器内监听可达地址，默认宿主端口发布绑定回环地址。对外访问的额外条件见安全规范。
- 持久化配置/数据库/用户产物使用命名卷或明确 bind mount；只读应用与可写数据分开。权限初始化要兼容非 root，不靠 chmod 777 解决。
- Linux 容器不得依赖 Windows 绝对路径、盘符或宿主安装的软件。用户文件通过上传/下载或显式挂载流转，指南分别说明。
- 镜像支持信号退出，回收子进程、停止接收新任务，按超时策略结束在途任务并保存状态。需要时使用 init 管理子进程。
- 健康检查使用真实可运行的检查入口，避免镜像中不存在的 curl 等命令；区分存活与就绪语义。
- 多服务启动依赖使用健康条件或成功完成条件，不以固定 sleep 等待。核心依赖就绪后才接受操作。
- 日志输出到标准输出/错误并限制保留；目录权限、数据空间不足等提供诊断。
- 默认重建、重启不会丢持久数据；带删除卷的命令需明确标记后果，不作为普通停止步骤。
- 单实例任务服务不配置多 worker；扩容前满足架构中的并发一致性条件。

实现后源码 checkout 的统一交付入口采用根 compose.yaml；可引用 deploy/ 内构建配置。是否提供镜像仓库、标签和访问权限需实际确定，不在规范中虚构镜像地址。

参考：[Docker Compose 卷](https://docs.docker.com/reference/compose-file/volumes/)、[Compose 启动与健康条件](https://docs.docker.com/compose/how-tos/startup-order)。项目约定应随实际配置同步验证。

## 5. 配置与数据一致性

所有形态使用同一配置模型和相同字段语义。差异只在路径、默认监听/端口、凭据来源及环境能力；指南提供形态对照表。

配置样例只有安全示例值，不含真实密钥。每个字段说明用途、类型、默认值、覆盖方式、是否敏感、是否需重启。配置/数据结构升级包含旧配置处理、备份、迁移和回退条件。

备份不能只复制正在写入的数据库文件；使用数据库支持的备份方法或受控停机快照。验证备份包含必要产物，并能在测试环境恢复。

## 6. 发布与验收

发布使用一致应用版本/源码提交标识；工具版本、公共协议版本和数据 schema 版本分别报告。CHANGELOG.md 的未发布条目按实际版本移动，保留 breaking changes 和迁移说明。

每次发行记录支持系统、运行时、镜像标签/摘要、构建方式、依赖许可与验证环境；发布前决定项目许可证，不能自行套用 MIT 等默认授权。

最低验收包括干净环境安装/构建、打开页面、深层路由、一个真实工具操作、错误提示、停止、重启后数据、可选依赖缺失、升级/恢复路径。桌面额外检查服务回收，Docker 检查卷和宿主文件边界。

本地构建与打包属于开发任务；推送镜像、发布安装包、部署远程服务等外部发布动作按用户授权执行。仅有规范本身无需发布审批。
