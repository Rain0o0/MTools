# 需求、开发与完成流程

## 1. 需求进入

从用户目标提取可观察的结果、影响范围和验收案例。用户未明确的常规实现细节采用符合规范的默认方案，记录必要假设；只有会明显改变范围、不可逆后果或缺失关键输入时才询问。

当前请求只交付规范时，不顺势搭建应用、安装依赖或宣布功能完成。后续实现以任务范围和项目当前状态为准。

## 2. 定位与拆分

先读 AGENTS.md 及相关专项规范，再查当前功能/问题/ADR。使用 rg 定位实际实现与相关消费方，不把整个仓库及所有日志加载进上下文。

普通任务直接实施。跨模块或多阶段任务在相关功能文档或工作记录写简短可验收步骤，每一步有具体产物与检查；不额外创建重复计划文件。路线图仅记录尚未完成的长期步骤。

## 3. 实施与记录

先建立必要契约和边界，再完成最小可用行为；遇到实际复用再抽取。新增依赖评估解决的问题、大小、许可、平台和 Docker 影响，更新锁文件，不为每个工具建立全套框架。

每批变更按 [版本迭代](../guides/versioning.md) 递增 minor 并维护 CHANGELOG，不以文档更新为例外；这来自用户明确要求。维持可审查的增量；保护已有代码/注释，禁止顺手清理。公开行为、配置、使用方法或支持形态变化，在同一批改动同步文档。默认不提交/推送仓库；若任务授权提交，提交信息准确概括最终变化。

阶段性反馈用中文说明已知事实、变化与尚未解决的风险，不以意图说明替代执行。不把可自行解决的常规细节转成审批节点。

## 4. 验证与评审

按测试规范执行相关检查；错误先分析、修复，再重复必要检查。不通过禁用测试、屏蔽错误或静默放宽规则制造“通过”。

自查关注真实风险：模块依赖、公开契约、环境能力、权限、数据迁移、任务副作用、失败恢复、源码/Docker 差异、中文界面和文档同步。不要以形式检查清单淹没简单任务。

## 5. 完成条件

- 用户授权范围内的行为已实现，或本次要求的规范/设计产物完整可读取。
- 改动边界清晰，实际检查有记录；未执行项与环境限制明确。
- 当前功能、使用说明与配置符合实现；索引、状态、变更日志和日期记录同步。
- 修复的问题已验证并从当前清单移除；未解决问题继续保留，未做功能继续留在路线图。
- 交付物可定位，源码与 Docker 相关改动满足声明支持形态；未实现的形态不得宣称可用。

交付用简短中文说明结果、入口、验证与必要限制。耗时工作应做完已授权部分，不停在“可继续”“建议下一步”等代替交付的提案上。
